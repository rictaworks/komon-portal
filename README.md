# komon-portal

A document portal for a labour and social security office and the client companies it serves.

When a document arrives, staff currently decide by eye which client it belongs to, rename it, file it, send it, and check that it was received. komon-portal does one thing with that work: it places each incoming document on the correct client's shelf without mix-ups, and records that the client received it. Case progress (submitted, document received, delivered, seen by the client) is updated from those records instead of being typed in.

The full design is in [`instructions.md`](instructions.md) (Japanese). The web UI is English only.

## Status

This is a work in progress. Only the parts listed under "Implemented" exist; everything else is planned and is not described here.

**Implemented on the development branch**

- Domain core (`src/core`, pure TypeScript): access policy, document intake and review, submission from clients, publishing, trash and purge, cases, invitations, memberships and first-time setup, audit recording.
- D1 schema (`src/app/migrations/0001_initial.sql`) and adapters for D1, R2 and the system clock.
- Auth API: Google sign-in (OpenID Connect with PKCE), sessions stored as hashes in D1, CSRF protection on state-changing requests, Turnstile checks for invitations and setup, and a development-only sign-in.

**Not implemented yet**

- Office and client web screens.
- Office and client APIs for intake, review, publishing, clients and cases.
- Classifier integration (Jev), Web Push notifications, scheduled maintenance, the admin Worker, and the release-triggered deploy workflow.

The page list and the full API list will be completed with the documentation issue.

## Stack

- Cloudflare Workers with [Hono](https://hono.dev) for the API
- Cloudflare D1 for data and R2 for files
- React 19 and Vite for the web UI, served as static assets by the Worker
- Google OpenID Connect for sign-in, Cloudflare Turnstile for human checks
- TypeScript in strict mode, Vitest with the Workers pool, ESLint

## Requirements

- Node.js 22 or later
- A Cloudflare account, with Wrangler available through the project's dev dependencies

## Local development

```bash
npm ci
cp .dev.vars.example .dev.vars
npm run dev
```

`npm run dev` builds the web UI and starts `wrangler dev`. Apply the migrations to the local D1 database once before the first run:

```bash
npx wrangler d1 migrations apply komon-portal --local
```

`.dev.vars` is git-ignored. Never commit it.

### Development sign-in

With `ENVIRONMENT=development`, `POST /api/dev/login` signs in as a ready-made test user without Google. It accepts a role of `owner`, `staff` or `member`. The `member` role belongs to a demo client (code `DEMO01`). This route does not exist in production.

Google sign-in needs `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. The redirect URI registered with Google is `<origin>/api/auth/callback`.

## Deployment

Each deployment serves one office, in that office's own Cloudflare account.

1. Create the database and bucket, then put the returned D1 ID into `wrangler.jsonc` in place of the placeholder:

   ```bash
   npx wrangler d1 create komon-portal
   npx wrangler r2 bucket create komon-portal-files
   ```

2. Apply the migrations to the remote database:

   ```bash
   npx wrangler d1 migrations apply komon-portal --remote
   ```

3. Set the secrets. Values are never stored in the repository.

   ```bash
   npx wrangler secret put GOOGLE_CLIENT_ID
   npx wrangler secret put GOOGLE_CLIENT_SECRET
   npx wrangler secret put TURNSTILE_SECRET_KEY
   npx wrangler secret put SETUP_TOKEN
   ```

   `TURNSTILE_SITE_KEY` is a public value in `wrangler.jsonc`. `ENVIRONMENT` must be `production`; any other value is an error.

4. Deploy:

   ```bash
   npx wrangler deploy
   ```

5. Create the first Owner. Sign in with Google, then call `POST /api/setup/claim` with the `SETUP_TOKEN` and a Turnstile token (`{"token": "...", "turnstileToken": "..."}`). The setup screen is not implemented yet. The token stops working once an Owner exists.

## Security and personal data

- Only Google's account ID (`sub`) and the display name are stored. The email address is never requested or stored, and IP addresses are not stored.
- Sessions are stored as hashes. The session cookie is `__Host-kp_session` (HttpOnly, Secure, SameSite=Lax), with a 60-minute idle timeout and a 12-hour limit.
- A client member can reach only the data of clients they belong to. Requests for other clients receive "not found".
- Original file names are not kept; names shown and downloaded are generated by the system.
- Documents containing an Individual Number (My Number) must not be submitted.
